# ADR 0004 — Backend API Boundary and Registration

## Status

Accepted

## Context

MiniRT is intended to be a kernel-first inference runtime where different implementations of expensive operations can be added, tested, benchmarked, and selected without rewriting the model execution path.

Without an explicit boundary, individual CUDA implementations may start depending on `ModelRunner`, scheduler state, KV allocator internals, or other implementation details.

This would make backend experiments difficult to isolate and would couple kernel code to the rest of the runtime.

MiniRT v0.1 therefore defines a small source-level backend API and a static registry.

A stable binary ABI or dynamically loaded plugins are not required.

## Decision

MiniRT v0.1 exposes three backend families:

```text
RmsNormBackend
GemmBackend
AttentionStageBackend
```

These are the only mandatory public extension points for v0.1.

Other operations such as:

```text
RoPE
activation
KV write
embedding
argmax
```

may initially remain internal implementations.

They can become public extension points later if there is a concrete need.

## Public / internal boundary

The repository is divided into public backend-facing headers and internal runtime implementation.

Public:

```text
include/minirt/core/
include/minirt/backend_api/
```

Internal:

```text
src/internal/
```

A backend may include headers only from:

```text
include/minirt/**
```

A backend must not include headers from:

```text
src/internal/**
```

This boundary must be enforced by the build system.

## Public core types

Backends may use a small set of common value/view types, for example:

```text
DType
LayoutId
TensorView
MutableTensorView
WorkspaceView
DeviceProperties
SupportResult
ExecutionContextView
```

These types describe data and execution resources but do not transfer runtime ownership to the backend.

Public interfaces must not expose:

```text
ModelRunner
RequestState
Scheduler
BlockPool
PersistentArena implementation
StepArena implementation
engine-owned containers
internal model state
```

## Backend ownership rules

The engine owns:

```text
model weights
activation buffers
KV-cache memory
CUDA streams
workspace memory
request state
scheduler state
```

A backend receives only views or handles to the resources needed for an operation.

A backend must not:

```text
allocate or free engine-owned KV blocks;
modify scheduler state;
modify request ownership;
perform hidden global synchronization;
perform device allocation inside the steady-state run path.
```

## Execution context

Every backend invocation receives an explicit CUDA execution context or stream.

Example:

```cpp
struct ExecutionContextView {
    cudaStream_t stream;
};
```

All CUDA work initiated by a backend must be submitted to the provided stream.

A backend must not silently switch to the default stream.

A backend must not call:

```cpp
cudaDeviceSynchronize();
```

inside the normal execution path.

## Support contract

Every backend must explicitly report whether it supports a given problem.

Example:

```cpp
struct SupportResult {
    bool supported;
    std::string reason;
};
```

Example behavior:

```text
supported:
  FP16, hidden_size=896, sm_75

unsupported:
  BF16 is not supported on the v0.1 backend

unsupported:
  hidden_size must be divisible by 8
```

Unsupported configurations must not silently fall back to another implementation.

Fallback selection belongs to the runtime/dispatcher and must be visible in execution metadata.

## RmsNormBackend

Candidate shape:

```cpp
struct RmsNormProblem {
    int64_t rows;
    int64_t hidden_size;
    DType dtype;
    float epsilon;
};

struct RmsNormArgs {
    TensorView input;
    TensorView weight;
    MutableTensorView output;
};

class RmsNormBackend {
public:
    virtual ~RmsNormBackend() = default;

    virtual SupportResult supports(
        const RmsNormProblem& problem,
        const DeviceProperties& device) const = 0;

    virtual void run(
        const RmsNormProblem& problem,
        const RmsNormArgs& args,
        ExecutionContextView context) = 0;
};
```

The exact C++ signature may evolve before the model path is stable.

The semantic boundary is the important part of this ADR.

## GemmBackend

`GemmBackend` represents linear/GEMM execution.

The problem description contains information such as:

```text
M
N
K
input dtype
weight dtype
output dtype
compute type
input layout
weight layout
output layout
transpose semantics
epilogue
```

The execution arguments contain the corresponding tensor views and workspace.

The model code must not know whether GEMM is implemented using:

```text
cuBLASLt
naive CUDA
tiled CUDA
future Tensor Core kernel
```

## AttentionStageBackend

Attention is exposed as a stage-level extension point rather than only as a single low-level kernel.

The stage boundary allows an optimized backend to fuse operations such as:

```text
RMSNorm + QKV projection
RoPE + KV write
RoPE + KV write + decode attention
```

without requiring changes to `ModelRunner`.

The backend may expose separate operations for:

```text
prefill
decode
```

because these workloads have different execution characteristics.

The engine owns KV-cache allocation.

Attention backends receive semantic views of contiguous or paged KV storage but never receive ownership of the KV allocator.

## Static backend registry

MiniRT v0.1 uses source-level static registration.

Example conceptual registry:

```cpp
class BackendRegistry {
public:
    void register_rmsnorm(
        std::string name,
        RmsNormBackendFactory factory);

    void register_gemm(
        std::string name,
        GemmBackendFactory factory);

    void register_attention(
        std::string name,
        AttentionBackendFactory factory);
};
```

Example backend names:

```text
rmsnorm_naive
rmsnorm_cuda_v1

gemm_cublaslt
gemm_naive
gemm_tiled_v1

attention_reference
attention_decode_v1
```

Dynamic `.so` loading and stable binary plugin ABI are outside the v0.1 scope.

## No backend-specific core branches

The following pattern is forbidden:

```cpp
if (backend_name == "my_attention_v2") {
    // special ModelRunner path
}
```

`ModelRunner`, scheduler, and KV allocator must operate against semantic backend interfaces rather than concrete backend names.

Adding a normal backend must not require changes to:

```text
ModelRunner
scheduler
request lifecycle
KV allocator
benchmark runner
other backend implementations
```

If a new backend genuinely requires a capability that the current API cannot express, the public contract must be changed explicitly instead of adding a backend-specific workaround.

## Backend selection

Backend choice is configuration-driven.

Conceptually:

```text
rmsnorm_backend = rmsnorm_cuda_v1
gemm_backend = gemm_cublaslt
attention_backend = attention_reference
```

The runtime:

1. looks up the requested backend in the registry;
2. asks `supports(problem, device)`;
3. either selects it or returns an actionable error;
4. records the selected backend in benchmark/result metadata.

There is no silent selection of a different implementation.

## API stability

The backend API is source-level and experimental during early v0.1 development.

A stable C++ binary ABI is not promised.

The API may change while RMSNorm, GEMM, contiguous attention, and paged attention are being implemented.

The first source-level API should only be considered stable after the paged attention path has validated that the interface is sufficiently expressive.

## Non-goals

v0.1 does not require:

* dynamic plugin loading;
* stable binary ABI;
* arbitrary user-defined operators;
* arbitrary computation graphs;
* public scheduler plugins;
* public KV allocator plugins;
* public memory allocator API;
* support for external model architectures;
* backend-specific command-line flags in core runtime.

## Consequences

Advantages:

* CUDA implementations remain isolated from engine internals;
* the same operation can have several implementations;
* kernels can be benchmarked and compared independently;
* `ModelRunner` remains backend-agnostic;
* future fusion is possible through stage-level backends.

Costs:

* backend interfaces require explicit problem and argument contracts;
* some capabilities may require API changes during early development;
* not every small internal operation is independently replaceable in v0.1.

## Verification

ADR 0004 is satisfied when the following questions have unambiguous answers:

1. Which backend families are public in v0.1?
2. Which headers may a backend include?
3. Which runtime objects are forbidden dependencies?
4. Who owns GPU memory and KV-cache blocks?
5. Which CUDA stream must a backend use?
6. How does a backend report an unsupported problem?
7. How is a backend registered?
8. How is a backend selected?
9. Can adding a backend require a special branch in `ModelRunner`?
10. Is stable binary plugin compatibility promised?

The expected answers are:

```text
Public backends:
  RMSNorm, GEMM, AttentionStage

Backend dependencies:
  public MiniRT headers only

Memory ownership:
  engine

Execution:
  supplied CUDA stream

Unsupported configurations:
  explicit SupportResult with reason

Registration:
  static BackendRegistry

Selection:
  configuration + registry + supports()

Backend-specific core branches:
  forbidden

Stable binary ABI:
  not promised
```
