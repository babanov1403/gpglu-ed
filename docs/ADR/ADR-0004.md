# ADR 0004 — Backend Boundary and Prepared Execution

## Status

Accepted; source API remains experimental until the M4 gate below.

## Public boundary

MiniRT v0.1 has three public backend families:

| Backend | Semantic operation |
|---|---|
| `RmsNormBackend` | RMSNorm with declared epsilon, dtype and layouts |
| `GemmBackend` | Linear/GEMM with explicit dimensions, orientation, accumulation and epilogue |
| `AttentionStageBackend` | Norm → QKV projection with bias → RoPE → KV write → attention → output projection |

Attention exposes separate prefill and decode operations. The stage returns the
projected attention output; the caller applies the residual. The reference stage
may compose configured RMSNorm/GEMM backends and internal primitives. A fused
stage preserves these semantics without fixing the number of kernel launches.
RoPE, KV write, SwiGLU, embedding, softmax and argmax remain internal primitives.
Model semantics and bias requirements are in [ADR-0001](ADR-0001.md).

Backends include only public `include/minirt/**` headers. Build checks prohibit
dependencies on `src/minirt/internal/**`, `ModelRunner`, request/scheduler state,
`BlockPool` and arena implementations. Public types describe tensor views,
named layouts, device properties, support results and execution resources.
They do not expose ownership of engine containers or allocators.

## Ownership and execution

The engine owns weights, packed-weight storage, activations, KV memory, streams,
workspace and request metadata. Backends receive bounded views/handles and may
own private host plan objects and library descriptors with explicit cleanup.
Every CUDA operation, including preparation work, uses the supplied stream.
Hidden default-stream work, `cudaDeviceSynchronize()` and scheduler/KV allocation
inside a backend are forbidden.

The engine retains all referenced resources until preparation and submitted
execution complete. Backend destruction follows completion of its outstanding
work. See [ADR-0005](ADR-0005.md) for iteration completion and reuse.

## Support, requirements, prepare, run

The lifecycle is semantic; exact C++ signatures may evolve before API freeze:

1. `supports(problem, device)` returns explicit support or an actionable reason,
   including dtype, layout, dimension, alignment and hardware restrictions.
2. Declare a `ShapeDomain`: either one exact shape, a bounded capacity domain,
   or an explicit finite set of shapes. It includes phase, batch/token/context
   bounds and relevant layouts. A bucket states which actual shapes it accepts
   and whether padding is required; padding must preserve masks and lengths.
3. `requirements(domain, device)` reports persistent and scratch byte/alignment
   requirements and metadata capacities. These are upper bounds for **every**
   accepted actual shape, including library workspace. Evaluating just the
   largest shape is insufficient when requirements are not monotonic.
4. The engine allocates resources. `prepare(domain, weights, resources, context)`
   receives weight/bias views, persistent storage, scratch resources, device
   information and the supplied stream. It returns a plan bound to the declared
   domain and resource lifetimes. It performs algorithm selection, descriptor
   creation, prepacking and constant-table preparation outside measured runs.
5. `run(plan, actual_problem, args, context)` validates that actual shapes/views
   satisfy the prepared domain and enqueues work using the provided resources.
   Actual token counts and context lengths remain explicit; capacity is not a
   substitute for their values. Domain overflow or insufficient workspace is an
   explicit error before launches or KV mutation.

Plans must state their stream/resource binding and permitted reuse. Prepare
failure cleans up partial descriptors and leaves engine resources releasable;
it cannot publish a partially usable plan. Asynchronous prepare work must finish
before those resources are released or used on an unordered stream.

There are no host/device allocations, descriptor creation, algorithm search,
lazy preparation or persistent-buffer growth inside `run()`. Any finite set of
shape-specific descriptors is created during prepare. After prepare/warmup,
model/engine iterations perform no device allocations and per-layer execution
performs no host allocations. Calls inside vendor libraries are included in
this contract and checked by the allocation audit.

A backend that cannot prepare a requested domain returns unsupported before
execution. The dispatcher may explicitly select another backend or a declared
set of prepared plans. Changing actual batch size does not authorize hidden
reprepare. New domains require an explicit setup boundary with updated memory
requirements, separate from steady-state execution and its timing.

## Registration and selection

The static registry maps unique backend names to family-specific factories.
Config selects a name for each family; the runtime checks support and records
the resolved backend, prepared domain and API version in result metadata.
Unsupported configurations never silently select another implementation.

`ModelRunner`, scheduler, KV manager and benchmark runner use semantic interfaces.
Adding a backend must not require branches on its name or edits to other
backends. If the contract lacks a needed capability, change the public contract
explicitly. Dynamic plugins and a stable binary ABI are outside v0.1.

## API freeze

The first source API becomes v1 only after M4 demonstrates all of the following:

- Contiguous prefill/decode and paged decode through registry/config selection.
- A fresh model request → prefill with paged KV population → first paged decode
  → repeated decode steps crossing a page boundary. Prepopulated KV fixtures
  alone do not satisfy this gate.
- Batch `1 → 4 → 2` with growing contexts on the same prepared domain/resources,
  without allocation, descriptor creation or lazy reprepare.
- Non-default stream execution, request isolation, release/reuse and correct
  resource upper bounds throughout those transitions.

Detailed conformance, memory audits and numerical comparisons are maintained
once in [validation.md](../validation.md), rather than duplicated per backend.
