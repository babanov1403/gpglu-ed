# ADR 0003 — Dtype, Numerics and Tensor Layouts

## Status

Accepted

## Context

MiniRT v0.1 needs one explicit numerical policy and a small set of tensor layouts.

Without this contract, different backends may silently use different precisions, accumulation rules, weight orientations, or tensor layouts, making correctness and performance results difficult to compare.

The target GPU is NVIDIA Turing `sm_75`.

## Decision

MiniRT v0.1 uses FP16 as the mandatory runtime data type.

### Runtime precision

```text
Weights:       FP16
Activations:   FP16
Outputs:       FP16

Reference:     FP32

GEMM accumulation:     FP32
RMSNorm accumulation:  FP32
Softmax accumulation:  FP32
```

The upstream Qwen2.5-0.5B checkpoint may store weights as BF16.

The MiniRT export step converts checkpoint weights to FP16 before they are loaded by the C++ runtime.

BF16 execution is outside the v0.1 scope.

## Operator numerics

### GEMM

Inputs and weights:

```text
A: FP16
B: FP16
```

Accumulation:

```text
FP32
```

Output:

```text
FP16
```

The reference path computes equivalent operations in FP32.

### RMSNorm

Input and weight are FP16.

The following calculations use FP32:

```text
sum(x²)
mean(x²)
rsqrt(mean(x²) + epsilon)
```

The final result is converted to FP16.

### Softmax / Attention

Attention scores and softmax reductions use FP32 accumulation.

Softmax must use numerically stable semantics:

```text
max_value = max(scores)
exp_value = exp(scores - max_value)
probability = exp_value / sum(exp_value)
```

The backend may fuse operations or avoid materializing intermediate FP32 tensors, but numerical behavior must satisfy the correctness suite.

### RoPE

Input and output activations are FP16.

Angle calculation and trigonometric calculations use FP32 in the reference implementation.

Backend implementations may optimize this representation if correctness remains within the declared tolerance.

## Math flags

v0.1 policy:

```text
TF32:      disabled / unsupported on target GPU
fast-math: disabled
```

Compiler or backend changes enabling relaxed numerical behavior require an explicit benchmark/research experiment and must be recorded in result metadata.

## Correctness tolerances

There is no single tolerance for every operation.

Initial v0.1 conformance tolerances are:

```text
RMSNorm / RoPE / KV write:
    atol = 2e-3
    rtol = 2e-3

GEMM:
    atol = 1e-2
    rtol = 1e-2

Attention / composed stages:
    atol = 2e-2
    rtol = 2e-2
```

Every comparison also records:

```text
max_abs_error
max_relative_error
relative_l2_error
NaN count
Inf count
```

Relative error around zero must not be used as the only correctness criterion.

Tolerances may be tightened after measurements.

They must not be silently relaxed to make a failing backend pass. Relaxing a tolerance requires a separate issue with a failing fixture and explanation.

## Tensor layout policy

MiniRT v0.1 does not implement a universal arbitrary-stride tensor system.

Instead, runtime tensors use a small set of named layouts.

### HiddenRowMajor

Transformer hidden states:

```text
[tokens, hidden_size]
```

The last dimension is contiguous.

For Qwen2.5-0.5B:

```text
[tokens, 896]
```

### LinearWeightOutIn

Linear-layer weights use:

```text
[out_features, in_features]
```

Examples:

```text
q_proj:    [896, 896]
k_proj:    [128, 896]
v_proj:    [128, 896]
o_proj:    [896, 896]

gate_proj: [4864, 896]
up_proj:   [4864, 896]
down_proj: [896, 4864]
```

This orientation matches the logical operation:

```text
Y = X × Wᵀ
```

### QkvTokenHeadDim

Q/K/V tensors use the semantic layout:

```text
[token, head, head_dim]
```

Examples:

```text
Q: [tokens, 14, 64]
K: [tokens,  2, 64]
V: [tokens,  2, 64]
```

### ContiguousKvLayerHeadTokenDim

The initial contiguous KV cache uses:

```text
[layer, kv_head, token, head_dim]
```

For the target architecture:

```text
[layer, 2, token, 64]
```

K and V are stored separately.

### PagedKvBlockHeadTokenDim

The later paged KV-cache uses a per-layer physical layout:

```text
[physical_block, kv_head, token_in_block, head_dim]
```

K and V are stored separately.

The block size is not fixed by this ADR and belongs to the KV-cache configuration.

### BlockTableRequestLogicalBlock

Paged KV block tables use:

```text
[request, logical_block]
```

Each entry identifies a physical KV block.

## Layout rules

Backends receive a named `LayoutId`.

A backend must either:

1. support the requested layout; or
2. return `unsupported` with an actionable reason.

Backends must not silently reinterpret memory using another layout.

Implicit layout conversion inside a benchmarked hot path is prohibited.

Any explicit conversion must be visible in execution metadata and measured separately when relevant.

## Alignment

v0.1 requires naturally aligned allocations from CUDA allocation APIs.

Additional alignment or vector-width requirements belong to individual backend capabilities.

For example, an optimized backend may require:

```text
pointer alignment >= 16 bytes
hidden_size % 8 == 0
```

Such restrictions must be reported through `supports()` rather than assumed globally.

## Non-goals

v0.1 does not require:

* BF16 execution;
* FP8 or quantized execution;
* arbitrary tensor strides;
* arbitrary layout permutations;
* automatic layout conversion;
* mixed-dtype backend dispatch;
* architecture-independent numerical behavior.

## Consequences

Advantages:

* all backends have the same numerical baseline;
* correctness comparisons are meaningful;
* weight orientation is unambiguous;
* layouts remain simple enough for learning and profiling;
* optimized backends may still impose stricter alignment/layout constraints.

Limitations:

* FP16 has lower numerical range than BF16;
* some newer-GPU optimizations cannot be studied on the target hardware;
* adding another architecture or dtype may require new conformance tolerances.

## Verification

ADR 0003 is complete when a developer can answer without guessing:

1. What dtype are model weights stored in?
2. What dtype are activations stored in?
3. Which operations accumulate in FP32?
4. What orientation do linear weights use?
5. What are the Q/K/V layouts?
6. What is the contiguous KV layout?
7. What is the paged KV layout?
8. What tolerances determine numerical correctness?
9. May a backend silently change layout or precision?

No item above may remain implicit before CUDA operator implementation begins.
