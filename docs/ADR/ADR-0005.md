# ADR 0005 — Paged KV, Admission and Scheduler Progress

## Status

Accepted for the v0.1 paged engine; implementation is planned for M4–M5.

## Paged storage and ownership

The engine preallocates a model-level pool of `C` blocks of `B` token slots.
One block ID identifies storage at that index in every layer's K and V arrays;
`C` counts complete model blocks, not individual layer pages. Physical layouts
are defined in [ADR-0003](ADR-0003.md).

Each request has a block table mapping logical blocks to physical block IDs.
For semantic position `p`, `logical_block = floor(p / B)` and
`offset = p % B`. A per-token slot mapping supplies the resolved block/offset
to kernels. Handles include a generation counter so release/reuse invalidates
stale references. Kernels receive views, never the allocator.

Block tables, slot mappings, free-list metadata, output slots and host/device
batch metadata have capacities fixed during engine setup. Assigning a logical
block from this pool is not a new device allocation. Tables and lengths expose
only initialized, request-owned positions; free slots and a partial page's tail
must not participate in attention.

## A fresh request: prefill → paged decode

The baseline processes one complete prompt with contiguous Q/K/V scratch.
At **each layer**, after Q/K/V projections and biases:

1. Apply RoPE to Q and K at prompt positions `0..L-1`.
2. Scatter post-RoPE K and unrotated V into the request's paged storage using
   the engine-provided slot mapping.
3. Compute causal prompt attention from contiguous scratch, then output
   projection and the remainder of the decoder block.

The scatter is part of prefill execution and its measured latency; temporary
Q/K/V storage is included in declared workspace. A future fused implementation
may write directly to pages if it preserves the same contract.

The last prompt position's logits produce the first output token. If it is EOS
or `MaxOutLen = 1`, the request finishes after prefill completion. Otherwise the
first decode consumes that token at position `L`, appends its per-layer K/V and
attends to the request's `L+1` valid positions. Each further decode consumes the
previous output token at the next position. Cache length counts consumed tokens;
output length counts generated tokens, including a terminal EOS.
After every generated token, finish if it is EOS or output length has reached
`MaxOutLen`; the final output token does not need to be appended to KV.

## Admission and capacity reservation

`MaxOutLen` (also called `max_new_tokens`) is a finite positive output-token
limit. Let `L` be prompt length and `N = MaxOutLen`. Admission reserves

```text
R = ceil((L + N) / B)
```

model blocks for the request's entire lifetime. This conservative bound includes
one slot beyond the last token normally consumed by a completed greedy request.
Configured context/position capacity must also cover `L + N`.

Reservation and assignment are distinct. `reserved(request) = R` is a quota;
`assigned(request)` is the number of physical blocks already in its table.
Maintain `assigned(request) <= reserved(request)` and
`sum(reserved(request)) <= C`. Free physical blocks therefore cover all admitted
requests' unassigned reservations. Growing decode assigns blocks against its
existing quota and cannot wait for another request to release memory.

Reservation, physical assignment and block-table updates are transactional.
Before execution, failure rolls them back without publishing partial ownership.
On completion or failure, release assigned blocks and the entire reservation
exactly once, after outstanding GPU access ends.

A request is permanently `Rejected` with a reason if its token IDs/lengths are
invalid, `L < 1`, `N < 1` or unbounded, `L` exceeds the configured prompt/workspace
capacity or `min(max_prefill_tokens_per_step, max_batched_tokens)`, `L+N` exceeds
context/position capacity, or `R > C`. These checks apply on submission, even if
older requests are waiting.
Integer arithmetic and block-table capacity checks must prevent overflow.

A valid request remains `Waiting` when active-request slots, unreserved block
capacity or the iteration's remaining token budget are temporarily insufficient.
It becomes `Admitted` only when its complete prefill fits the remaining budget
and its full reservation and metadata slot can be acquired together.

## Baseline scheduling policy

All configured capacities and budgets must be positive and satisfy:

```text
max_decode_requests_per_step >= max_active_requests
max_batched_tokens >= max_active_requests
max_prefill_tokens_per_step <= max_batched_tokens
```

`max_batched_tokens` limits the combined decode and prefill input tokens in one
iteration. Setup rejects configurations whose prepared domains or buffers do
not cover these maxima and the configured maximum prompt/context.

An iteration uses a snapshot of completed state:

1. Schedule one decode token for **every** active decoding request. If there are
   `D` such requests, the remaining token budget is `max_batched_tokens - D`.
2. Admit at most one waiting request, in FIFO order, only if its whole prompt
   fits that remaining budget and an active-request slot and its full reservation
   are available. Schedule its complete prefill. Otherwise leave it waiting;
   do not bypass it with younger requests. Thus
   `decode_tokens + prefill_tokens <= max_batched_tokens` in every iteration.
3. Execute the decode sub-batch, then the optional prefill sub-batch, on the
   supplied stream. These are separate calls with separate valid metadata.
4. Observe iteration completion, publish generated tokens, update lengths and
   terminal states, and release completed requests' blocks/reservations.

Capacity released in step 4 becomes available to the next iteration. Arrivals
join the queue between iterations. There is no chunked prefill or mixed packed
prefill/decode execution in this baseline.

Lifecycle is `Waiting → Admitted → Prefilling → Decoding → Finished`, with a
direct `Prefilling → Finished` for the terminal first token. Permanent admission
errors lead to `Rejected`; execution errors lead to `Failed`. Terminal requests
are never scheduled again.

Every admitted decoding request advances once per successful iteration and has
a finite output limit. Full reservation removes decode allocation deadlocks.
FIFO admission and rejection of impossible requests ensure a waiting request
eventually fits after earlier requests finish, assuming GPU work completes and
the engine continues iterating. A long prompt at the head of the queue may wait
while active decodes consume the shared token budget. Those requests eventually
reach EOS/MaxOutLen and drain; the whole prompt then fits an otherwise empty
iteration. Younger requests cannot overtake it and keep the engine occupied.
A long prefill may increase token latency; this baseline makes no
latency-fairness guarantee.

## Completion, reuse and failure

v0.1 uses one supplied execution stream and at most one outstanding iteration.
The engine observes an explicit CUDA event/stream completion before publishing
results, changing state used by execution, overwriting batch metadata, resetting
scratch, recycling request slots or releasing/reusing KV blocks. Decode and
prefill metadata must remain valid until their consumers finish; sharing scratch
is allowed only with ordered accesses on that stream.

A validation/planning failure before enqueue publishes no tokens and rolls back
new reservations/assignments. Report the error and mark affected admitted
requests `Failed`; unaffected requests retain their last completed state.
A failure after enqueue may leave KV partially
written: fail every request included in that iteration, publish no partial
outputs and do not retry from the mutated cache. Drain/observe outstanding work
before cleanup. If completion cannot be established or CUDA context integrity
is lost, stop the engine, fail remaining requests and tear down the affected
resources instead of returning blocks to a reusable pool.

The required boundary, reservation-pressure, progress and batch-failure tests
are in [validation.md](../validation.md). Prepared capacity and allocation rules
are in [ADR-0004](ADR-0004.md).
